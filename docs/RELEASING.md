# Publishing a KyoHUD release

This document is the tracked, authoritative procedure for publishing KyoHUD. It
covers the versioning scheme, the exact steps for the first public release
(v1.0.0), and the checklist to repeat for every later release.

Nothing in this file is loaded by the game. `docs/` is excluded from the
published mod archive.

## Versioning

KyoHUD uses semantic versioning from v1.0.0 onward.

- `mod.txt` carries the bare version: `"version": "1.0.0"`.
- The Git tag carries the same version with a `v` prefix: `v1.0.0`.
- `changelog.txt` entries are headed `vMAJOR.MINOR.PATCH (DD.MM.YYYY):`, newest
  first.
- `meta.json` is **generated by the release workflow**. It is not tracked in the
  repository and must not be committed.

Version bump rules:

| Change | Bump |
| --- | --- |
| Breaking change to saved settings, option identifiers, or the public mod identity | MAJOR |
| New feature, new option, new HUD element | MINOR |
| Bug fix, wording, rendering correction, tooling fix with no user-facing feature | PATCH |

Pre-1.0 history used integer revisions (`r62` … `r84`). Those entries stay in
`changelog.txt` as the historical record and are never rewritten. Legacy `rN`
tags are not deleted; the release workflow no longer accepts them.

## Tag format enforcement

`.github/workflows/release.yml` validates, before building anything:

1. The release tag is exactly `v` followed by three dot-separated numbers with
   no leading zeros — `\Av(?:0|[1-9][0-9]*)(\.(?:0|[1-9][0-9]*)){2}\z`,
   case-sensitive, no surrounding whitespace.
2. `mod.txt`'s `version` matches the same pattern without the `v`.
3. The tag equals `"v" + mod.txt version`, character for character.

Any mismatch fails the job. Rejected examples: `r84`, `1.0.0`, `V1.0.0`,
`v1.0`, `v1.0.0-rc1`, `v1.0.0.0`, `v01.0.0`, `v1.0.0 ` (trailing space).
Accepted: `v1.0.0` when `mod.txt` reads `"version": "1.0.0"`.

## First public release: v1.0.0

Perform these steps in order. Steps 1-3 happen on the work branch, step 4
onward on `main`.

### 1. Prepare the release commit on the work branch

- [ ] `mod.txt` reads `"version": "1.0.0"` and the public name is unchanged:
      `KyoHUD - Killfeed & Combat Score`.
- [ ] `changelog.txt` starts with the `v1.0.0 (01.09.2026):` entry.
- [ ] `README.md` documents Versioning, Releases, and the restriction against
      re-uploading KyoHUD without permission or presenting it as someone else's
      work.
- [ ] `CREDITS.md` is current; `.github/7ZIP_LICENSE.txt` and
      `.github/TOOLS.md` are unchanged and still describe the shipped tooling.
- [ ] No `meta.json` is tracked: `git ls-files meta.json` prints nothing.
- [ ] `git diff --check` is clean and `git status --short` shows only intended
      files.

Commit the branch and open a pull request into `dev`.

### 2. Merge into `dev`

- [ ] The pull request targets `dev`, not `main`.
- [ ] After merge, `dev` contains the v1.0.0 version bump and changelog entry.

### 3. Merge `dev` into `main`

`main` is the published branch.

```sh
git fetch origin
git switch main
git merge --ff-only origin/main      # confirm main is up to date
git merge --no-ff origin/dev -m "release: v1.0.0"
git push origin main
```

- [ ] `main` now contains exactly the tree that will be published.
- [ ] `git show main:mod.txt` reports `"version": "1.0.0"`.

### 4. Tag and create the GitHub release

Tag the merge commit on `main`, never a branch tip that is still moving.

```sh
git tag -a v1.0.0 -m "KyoHUD v1.0.0" main
git push origin v1.0.0
```

Then create the GitHub release from that tag:

```sh
gh release create v1.0.0 \
    --target main \
    --title "KyoHUD v1.0.0" \
    --notes-file docs/RELEASE_NOTES_v1.0.0.md \
    --latest
```

- [ ] The release is published (not a draft) — the workflow triggers on
      `release: published`.
- [ ] The release is marked **Latest**. SuperBLT resolves updates through
      `releases/latest/download/`, so a release that is not latest will not be
      served.
- [ ] The release is not marked as a pre-release.

### 5. Watch the workflow validation

`Build SuperBLT release assets` runs on `windows-latest` and must pass all of:

- [ ] **Check out the released revision** — checks out the tag itself.
- [ ] **Validate tag and mod version** — the three checks described above.
- [ ] **Test SuperBLT hashing implementation** —
      `python .\.github\test_superblt_hash.py -v` passes.
- [ ] **Stage the distributable mod** — copies every tracked file except
      `.github/`, `docs/`, `.gitattributes`, `.gitignore`, `AGENTS.md`,
      `CODEX.md`, and `meta.json` into `release-stage/Kyohud`, and fails if
      `mod.txt` is missing from the staged tree.
- [ ] **Build latest.zip and SuperBLT metadata** — the directory hash is a
      64-character lowercase hex string and the generated metadata is a JSON
      array with exactly one valid entry.
- [ ] **Upload SuperBLT assets** — uploads with `--clobber`.

If a step fails, fix the cause on a branch, merge it forward through `dev` and
`main`, bump to the next patch version, and tag again. Do not move an existing
tag.

### 6. Verify the generated assets

The release must carry exactly two generated assets.

- [ ] `latest.zip` is attached and contains a single top-level `Kyohud/`
      directory holding `mod.txt`, `mod.png`, `lua/`, `menu/`, `loc/`,
      `README.md`, `CREDITS.md`, and `changelog.txt`.
- [ ] `latest.zip` contains no `.github/`, no `docs/`, no `AGENTS.md`, no
      `CODEX.md`, and no `meta.json`.
- [ ] `meta.json` is attached and is a JSON **array** with one object holding
      `ident` (`kyohud`), `hash` (64 lowercase hex characters),
      `patchnotes_url`, and `download_url`.

Spot-check the published URLs:

```sh
curl -sL https://github.com/Kyosh1ro/kyohud/releases/latest/download/meta.json
curl -sIL https://github.com/Kyosh1ro/kyohud/releases/latest/download/latest.zip
```

- [ ] The `meta.json` served from `releases/latest/download/` is the one from
      this release.
- [ ] `latest.zip` resolves to a `200` response.

### 7. Verify in PAYDAY 2 with SuperBLT

Static validation never proves engine compatibility. This step is mandatory
before announcing the release.

- [ ] Extract `latest.zip` so the mod lands in `PAYDAY 2/mods/Kyohud/`, with
      `mod.txt` directly inside that folder.
- [ ] Launch PAYDAY 2 with SuperBLT and confirm the mod loads with no
      `[KyoHUD]` errors in the SuperBLT log.
- [ ] `Options > Mod Options > KyoHUD - Killfeed & Combat Score` opens, and all
      sliders, toggles, and submenus respond.
- [ ] Run **Preview Buffs & Kills** through its cases, then **Clear Preview**.
- [ ] In a real heist: a buff appears and refreshes without duplicating, a
      direct kill and a projectile kill both register, the killfeed orders
      cards oldest-left, and the score widget shows Total Score and Best
      Streak.
- [ ] Update path: with an older KyoHUD installed, SuperBLT's mod-update check
      detects v1.0.0, downloads it, and the mod loads after restart.

### 8. After publishing

- [ ] The release page renders the notes correctly.
- [ ] `dev` and `main` point at the same tree.
- [ ] Post-release work restarts from a fresh `fix/<topic>` or
      `feature/<topic>` branch off `origin/dev`.

## Subsequent releases

Repeat sections 1-8 with the new version, replacing `1.0.0` throughout and
using `docs/RELEASE_NOTES_v<version>.md` for the notes. The short form:

1. Branch from `origin/dev`; bump `mod.txt`; prepend the changelog entry.
2. Merge to `dev`, then merge `dev` into `main`.
3. Tag `vN.N.N` on `main` and publish the GitHub release as **Latest**.
4. Confirm the workflow is green and both assets are attached.
5. Verify the mod in-game with SuperBLT, including the update path.

## Rebuilding assets without a new release

`workflow_dispatch` rebuilds the assets of an existing tag:

```sh
gh workflow run "Build SuperBLT release assets" -f tag=v1.0.0
```

The same tag validation applies, so the tag must already satisfy `vN.N.N` and
match its own `mod.txt`.
